Dedicated Cloudflare D1 database: `jawed-studio-hq`.

- Identity: `hq_users` stores the two owner identities after server-side authorization.
- CRM: `clients`, `client_contacts`, `activity_notes`.
- Projects and delivery: `projects`, `project_milestones`, `project_tasks`, `repositories`, `deployments`.
- Approval and QA: `approvals`, `qa_checks`.
- Finance: `quotations`, `invoices`, `payments`, `maintenance_plans`.
- Assets and knowledge: `assets` stores metadata and external storage references, not file bytes.
- Security: `audit_logs` is append-only.

## Data conventions
- IDs are UUID strings generated by the application.
- Timestamps are UTC ISO-8601 strings.
- Money is integer minor units (paise for INR), never floating point.
- Business records use `archived_at` and `archived_by` for reversible soft deletion.
- Foreign keys use RESTRICT to prevent accidental cascade deletion.
- Audit logs reject UPDATE and DELETE through SQLite triggers.
- File content should live in an approved object store or versioned repository, not D1.

## Security boundary
D1 must only be accessed from the Worker after Firebase ID-token verification and exact owner allowlist authorization. Never expose D1 credentials or database bindings to browser code. Every mutating API must write an audit event in the same logical operation where possible.

## Before applying
1. Confirm the database name and create the dedicated D1 database only with explicit approval.
2. Add a Worker binding named `HQ_DB` to the dedicated database ID.
3. Add a migration directory mapping for this schema.
4. Run migration against a non-production preview database first.
5. Verify foreign keys, indexes, archive/restore behavior, audit immutability, and rollback/recovery procedure.
